Documentation: Keenly Jagged II Perk Implementation
Overview
Successfully implemented the Keenly Jagged II perk, which applies a bleed (DoT) effect on critical hits. This was the first DoT (Damage over Time) perk implemented in the system and required building the entire DoT infrastructure from scratch.

Perk: Keenly Jagged II
Effect: On critical hit, apply bleed that deals 11% weapon damage per second for 10 seconds
Stacking: NO STACKING - Only one Keenly Jagged bleed can be active at a time
Refresh: NO REFRESH - Additional crits while bleed is active are blocked

Tick calculation system processes DoTs at 1-second intervals

Ticks process at regular intervals (every 1.0s for bleeds)

Key Learnings
1. DoT Tick Timing Architecture
Problem: DoTs need to "tick" at regular intervals (e.g., every 1 second), but the engine processes events at irregular timestamps.

Solution: Pre-calculate all tick times and insert synthetic DOT_TICK events

Lesson: DoTs are fundamentally different from instant effects - they need special time-based processing logic.

2. DoT Anti-Stacking Behavior
Problem: Should Keenly Jagged bleed stack with itself? Should it refresh?

Decision: NO STACKING, NO REFRESH - Only one instance can exist at a time

Solution: Check for existing DoT by effect ID before applying

Lesson: Different DoT types (Keenly Jagged vs. Poison, etc.) can coexist, but each type anti-stacks with itself by checking e.id === effectData.id.

3. Effect Category Stacking Rules
The Complete Picture:

Category	Stacking Rule	Refresh Rule	Cap	Notes
DOT	Anti-stack by id	NO refresh	None	One instance per DoT type
EMPOWER	Stack across sources	Refresh by sourceId	50%	Same source refreshes, different sources stack
REND	Stack across sources	Refresh by sourceId	70%	Same source refreshes, different sources stack
FORTIFY	Stack across sources	Refresh by sourceId	50%	Same source refreshes, different sources stack
MISC_DAMAGE	Stack unlimited	Refresh by sourceId	UNCAPPED	No limit
HEAL	Instant (N/A)	N/A	None	Applies immediately, not stored
Examples:

Lesson: Anti-stacking logic varies by category:

DoTs check by effect ID (e.id === effectData.id)
Buffs/debuffs check by source ID (e.sourceId === effectData.sourceId)
4. DoT Damage Calculation
Problem: DoT damage needs to snapshot the stats at application time, not recalculate on each tick.

Solution: Store damage value in effect metadata

Lesson: DoTs should "snapshot" their damage at application time to avoid recalculating with changed stats.

5. Event vs. Effect Distinction
Problem: Confusion between "events" (player actions) and "effects" (consequences of events).

Clarity:

Event: Player action (Light Attack, Block, ability cast)
Effect: Consequence applied to combatant (bleed, empower, heal)
DoT Tick: Synthetic event generated by engine, not player action
Lesson: DoT ticks are "synthetic events" - they're not in the rotation, but are generated by the engine based on active DoT effects.

6. DoT Expiration and Cleanup
Problem: DoT effects need to be removed from activeEffects when they expire.

Solution: Filter expired effects before processing ticks

Lesson: Always clean up expired effects before processing to avoid ticking dead DoTs.

Common Pitfalls to Avoid
Don't allow DoT stacking - Check by id, block if exists
Don't refresh DoT duration - No refresh logic for DoTs
Pre-calculate tick times - Don't try to tick "on demand"
Snapshot damage values - Don't recalculate with current stats
Clean up expired DoTs - Filter them before processing ticks
Use category: 'DOT' - Don't mix with other effect types
Store metadata - Include tickInterval, damagePerTick, sourceName
Handle DoT_TICK events - They need special processing in the event loop
Remember: Anti-stack by ID - e.id === effectData.id, not by source
